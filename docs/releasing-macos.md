# macOS CI, signing, and updates

Calum configures the credentials below in this repository's **Settings → Secrets
and variables → Actions → Secrets**. No credential values belong in source,
release notes, issue comments, or workflow YAML. The workflows use GitHub's
provided token; a personal access token is not needed.

## Prepare a release

Start on a clean, up-to-date `main` with the full tag history available:

```sh
cargo xtask release patch
# Equivalent explicit preview; also accepts minor, major or X.Y.Z:
cargo xtask release --dry-run patch
```

The default is an offline, read-only plan. It prints the version reference and
lockfile diff, generated changelog section, release notes and every subsequent
step. Remote freshness, tag availability and CI are listed as deferred checks;
the preview does not fetch, call `gh`, create refs or write files. Cargo itself
may compile xtask before starting it. Version files reuse `bump-version`; Info.plist
is generated by packaging from that version rather than maintained separately.

After reviewing the plan, explicitly authorize local preparation:

```sh
cargo xtask release patch --execute
```

This checks a clean tree on `main`, compares HEAD with live `origin/main` using
`git ls-remote`, rejects existing local/remote tags, and requires all HEAD GitHub
check runs to be completed successfully. Missing, skipped, pending, failed or
more than 100 checks fail closed. Read-only Git/`gh` calls use the injectable
command runner. It then creates `chore/release-vX.Y.Z`, applies the version bump,
refreshes Cargo.lock offline, prepends CHANGELOG.md and commits
`chore(release): vX.Y.Z`. It prints a `gh pr create` command for the operator;
it does not push the branch or open a PR. Push the branch through the normal
review process, then squash merge with that exact commit title. A failure after
branch creation leaves the local branch and any completed edits for inspection;
version-update failures retain the existing planner's rollback behavior.

The changelog groups `feat`, `fix`, `perf` and `refactor`; all other subjects
(including non-Conventional Commits) appear under **Other**. Merge commits are
excluded. Scopes are accepted, `(#N)` suffixes become PR links, and `!` or
`BREAKING CHANGE:` / `BREAKING-CHANGE:` footers also populate **Breaking changes**.
History starts after the highest reachable stable `vX.Y.Z` tag (all history for
the first release). Empty history says **No changes**. Sections have no generated
date, so identical inputs produce identical output. Existing changelog bytes
remain below the new section. The release workflow reads the section from the
tagged CHANGELOG.md and combines it with its signed/unsigned installation
template for DMG/appcast notes; older tags without a changelog retain subject-based
notes. Review generated text before approving the release PR.

After the PR merges, update `main` and obtain separate release authorization:

```sh
cargo xtask release tag             # offline preview
cargo xtask release tag --execute   # creates AND pushes the annotated tag
```

Tag execution repeats preflight and requires main HEAD to be the single-parent
squash-merged `chore(release): vX.Y.Z` commit with the matching latest changelog
section and workspace version. It tags that verified SHA and pushes only
`refs/tags/vX.Y.Z`. If pushing fails, the local tag remains: inspect it and resolve
the failure deliberately; never overwrite an existing published tag.

The existing **Release macOS** tag workflow then builds, signs, notarizes, staples,
creates the DMG and signed appcast, and publishes the GitHub release; **Deploy
site** follows successful publication. Credentials and real macOS qualification
below remain prerequisites. Fixture tests prove command orchestration, not Apple
service behavior or a shipped release; shipping v0.3.2 remains tracked in #88.

## Secrets to create

| Secret | Value and source |
| --- | --- |
| `MACOS_CERTIFICATE_P12_BASE64` | Base64 of a password-protected Developer ID **Application** `.p12` export, including its private key. |
| `MACOS_CERTIFICATE_PASSWORD` | The nonempty password chosen when exporting that `.p12`. |
| `MACOS_SIGNING_IDENTITY` | Optional: the certificate's SHA-1 fingerprint. Omit when the export contains exactly one valid Developer ID Application identity; the packager auto-detects it. |
| `APPLE_API_KEY_P8_BASE64` | Base64 of the downloaded App Store Connect **team** API `.p8` key. Assign the key the **Developer** role. |
| `APPLE_API_KEY_ID` | The API key's Key ID from App Store Connect. |
| `APPLE_API_ISSUER_ID` | The team API Issuer ID from App Store Connect. |
| `SPARKLE_ED_PRIVATE_KEY` | The **contents** of the private key file exported by Sparkle `generate_keys -x`. It is already base64; do not base64-encode it again. |

The public Sparkle key is committed in
`packaging/macos/sparkle_public_ed_key.txt` as canonical base64 of 32 bytes.
Every packaged build embeds Sparkle, including ad-hoc CI packages. The optional
Actions **variable** `SPARKLE_PUBLIC_ED_KEY` (or local environment variable) still
supplies the key when set, but must match the committed key. A missing/invalid
file or mismatched override fails packaging; there is no silent key change or
update-free package. No Actions variables are required.

Read-only inventory on **2026-10-26**: `gh secret list -R 0x63616c/voxelite
--json name,updatedAt` and `gh variable list -R 0x63616c/voxelite --json
name,updatedAt` both returned empty lists. All six required repository secrets
above are missing; `MACOS_SIGNING_IDENTITY` is optional. This inventory confirms
names only, not credential validity or organization/environment inheritance.
No secrets or variables were set during implementation.

### Developer ID certificate

1. In the Apple Developer account, create a **Developer ID Application**
   certificate using a certificate signing request from Keychain Access, or use
   an existing valid certificate. Install it on the Mac holding its private key.
   Developer ID Installer and Apple Distribution certificates are not suitable
   for this app. See [Apple's Developer ID certificate guide](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/).
2. In **Keychain Access → My Certificates**, expand the certificate and confirm
   the private key is present. Select the certificate/private-key pair, choose
   **Export**, and save as **Personal Information Exchange (.p12)** with a strong,
   nonempty export password. Keep the export outside the checkout.
3. Set `MACOS_CERTIFICATE_PASSWORD` using the GitHub secrets UI (or `gh secret set`
   interactively). On macOS, encode and upload the export without printing it:

   ```sh
   base64 -i /secure/path/developer-id.p12 | tr -d '\n' |
     gh secret set MACOS_CERTIFICATE_P12_BASE64 --repo 0x63616c/voxelite
   ```

4. Normally omit `MACOS_SIGNING_IDENTITY`. If the export contains multiple
   Developer ID identities, inspect `security find-identity -v -p codesigning`
   locally and save the selected fingerprint in that secret. Do not copy the
   identity listing into the repository or CI logs.

### App Store Connect notarization key

In **App Store Connect → Users and Access → Integrations → App Store Connect API
→ Team Keys**, generate a team key with **Developer** access. An Account Holder or
Admin creates the team key; API access may first need approval. Download its `.p8`
file when offered, and save the displayed Key ID and Issuer ID in the corresponding
secrets. This workflow supplies an issuer and requires a team key. See Apple's
[API key instructions](https://developer.apple.com/documentation/AppStoreConnectAPI/creating-api-keys-for-app-store-connect-api)
and [notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).

```sh
base64 -i /secure/path/AuthKey.p8 | tr -d '\n' |
  gh secret set APPLE_API_KEY_P8_BASE64 --repo 0x63616c/voxelite
```

Keep the downloaded key and certificate export in secure storage outside the
checkout. The packaging task decodes them into a private temporary directory,
imports the certificate into a temporary keychain, grants noninteractive
`codesign` access, and restores the runner's keychain search list on exit. Cleanup
also runs on failures, `INT`, and `TERM`, including when the original keychain
search list is empty. A forced kill or machine outage cannot run cleanup guards;
inspect the runner for leftover temporary keychains before resuming releases
after such an interruption. Do not run packaging with shell tracing. Raw signing
and authentication diagnostics are suppressed on failure because they can expose
certificate identities; reproduce locally to inspect Apple tool errors.

## CI behavior

`.github/workflows/ci-macos.yml` runs on pushes to `main` and same-repository pull
requests. Its job-level guard is:

```yaml
if: github.actor == '0x63616c' && (github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository)
```

Fork pull requests never schedule this self-hosted job. Do not change the event to
`pull_request_target` or remove the guard. The release job has the same guard.

All three self-hosted jobs (CI macOS, Rendering checks, Release) use the labels
`[self-hosted, macOS, ARM64, xcode]`, which select the self-hosted Apple Silicon runner, with
`DEVELOPER_DIR=/Applications/Xcode-27.0.app/Contents/Developer`. There are no
GitHub-hosted macOS jobs. CI macOS runs its Python script tests on a GitHub-hosted
Linux runner, and builds the ad-hoc DMG only on pushes to `main` and on pull
requests that change packaging inputs (`packaging/`, `xtask/`, Cargo
manifests, the toolchain or the macOS workflows).

Rendering visual runs (PRs, `visual`, `rebaseline-visual`) use either Mac mini
runner. Both runners are on the same machine, and homelab-voxelite-2 rendered
every still bit-exact against the committed goldens with `--determinism` before
the pin was lifted (#165). `bench` and `bench-baseline` always use the runner with
the `golden` label, so timing baselines come from one place. The owner-only
`runner_label` dispatch input (`any`, `golden`, `runner-2`) re-checks one runner;
verify any new runner this way before it takes visual jobs. Runner layout and the
build caches are described in [CI runners](ci-runners.md). The runner needs that Xcode installation and its Metal
toolchain, the Rust toolchain from `rust-toolchain.toml` including rustfmt/Clippy,
Python 3, curl, and GitHub CLI for releases. The runner must support
the v4 checkout and artifact actions, pinned to commit SHAs in the
workflows.

CI checks formatting, runs the mocked packaging/release regression tests,
runs `cargo clippy --workspace --locked -- -D warnings`,
runs `cargo test --workspace --locked`, builds the release app, and packages a
DMG. Strict Clippy passed on Linux when this workflow was added; the first macOS
run must confirm the platform-specific code too. `MACOS_SIGNING_MODE=adhoc`
forces an ad-hoc app and unsigned DMG even if the runner has signing credentials.
No signing/notarization secrets are passed to CI. Its DMG and checksum artifacts
expire after **3 days**. New runs cancel older CI runs for the same ref.

## Release behavior

The release workflow is triggered by `v*` tags or manual dispatch with an
existing tag. It accepts stable `vMAJOR.MINOR.PATCH` tags only and checks out the
fully qualified `refs/tags/` ref, so a same-named branch cannot supply the build.
The tag without `v` must equal the `voxelite-app` Cargo version and supplies both
bundle version fields. Bump the workspace version and lockfile before tagging. Use an
increasing version for each public update and keep published release tags/assets
immutable; the update feed depends on their exact bytes. Releases serialize and
are not cancelled in progress. Publication creates a draft, uploads the DMG,
checksum, signed release notes, and signed feed together, then publishes only after every upload
succeeds. An existing release (including a draft) makes publication fail; assets
are never overwritten. A failed upload leaves a draft for inspection. Remove
that unpublished draft manually before retrying, or use a new version tag.

The packager:

1. Builds `voxelite-app` with the locked dependencies and assembles the app/icon.
   Release CI builds in a separate step without signing credentials, then invokes
   the packager with `--skip-build` and an explicit `VERSION`. Local packaging
   still builds by default. The task removes credential variables from child
   environments and decodes the keys in-process.
2. Validates the committed public key and optional matching override, downloads
   pinned Sparkle 2.10.1, verifies SHA-256, preserves framework symlinks, and embeds
   the framework and license. It sets the feed, key, and update policy described
   below in the built Info.plist.
3. With a certificate and password, signs the Sparkle XPC services, helper tool,
   updater app, framework, and outer app in that order, using the same Developer
   ID, hardened runtime, and secure timestamps. The app uses
   `packaging/macos/Voxelite.entitlements`; the empty entitlement dictionary keeps
   library validation enabled. Downloader entitlements are preserved. See
   [Sparkle's manual signing guidance](https://sparkle-project.org/documentation/sandboxing/#code-signing).
4. With all three API credentials, notarizes a ZIP of the app, requires an
   `Accepted` result, staples and validates the app, and checks it with `spctl`.
5. Builds the DMG containing that stapled app and the Applications shortcut, signs
   and notarizes the DMG, staples/validates it, and runs the DMG Gatekeeper
   assessment. It computes SHA-256 **after** the final staple. The checksum names
   `Voxelite.dmg` without a directory prefix, so both downloaded assets can be
   checked together with `shasum -a 256 --check Voxelite.dmg.sha256`.
6. Deletes its temporary keychain and working files on exit.

Without the certificate/password pair, the build succeeds with ad-hoc app signing
and an unsigned DMG. With Developer ID but incomplete API credentials, it signs
without notarizing. These local/CI modes print clear notices. The release workflow requires all five
Apple secrets and appcast generation requires a notarized result and the Sparkle
secret; an incomplete configuration cannot publish a release.
Invalid credentials, rejected notarization, bad checksums, or failed signature
verification fail the release; they do not silently fall back. Ad-hoc builds omit
hardened runtime so they can load the ad-hoc Sparkle framework during development.

The runtime updater loads only `Contents/Frameworks/Sparkle.framework/Sparkle`
from the app bundle, through `dlopen`. It retains the Objective-C controller and
framework for the process lifetime. Non-bundle `cargo run` and bundles without
Sparkle work normally. The app menu and Settings > Updates both call
`crate::updater::check_for_updates()` on GPUI's main thread. Their availability
query, `is_available()`, reads the controller's updater `canCheckForUpdates`, so
validation disables checks while Sparkle is busy or unavailable. Dispatch checks
that property again. The controller starts with `initWithStartingUpdater: true`.
Verify that menu/Settings presentation refreshes when the updater changes state.
Only this macOS module permits the unsafe Objective-C calls; the app's other code
denies unsafe code, and other crates retain the workspace forbid lint.

## Automatic updates (Sparkle)

### Policy and key custody

The production feed is `https://voxelite.worldwidewebb.co/appcast.xml`.
`SUEnableAutomaticChecks=true` starts automatic checks when the updater starts
at launch, subject to Sparkle's remembered last-check time and default daily
interval. `SUAutomaticallyUpdate=false` requires user approval before downloads
and installation by default; users can opt into automatic downloads in Sparkle's
update dialog. Neither setting forces a preference the user has already changed.
System profiling remains off. See [Sparkle's settings](https://sparkle-project.org/documentation/customization/).

`SUVerifyUpdateBeforeExtraction=true` and `SURequireSignedFeed=true` retain
archive and metadata signature verification. There is no unsigned installable
fallback. Before the first signed release, the checked-in RSS feed is valid and
empty: `/appcast.xml` exists but contains no update items. A signed-feed client
may report a verification error for this unsigned bootstrap feed; the first
signed release replaces it. Older builds that never embedded Sparkle require a
manual installation of v0.3.0 or later, which includes Sparkle.

The existing production private key lives only at
`/home/box/secrets/voxelite-sparkle/sparkle_ed_private_key.txt`. It must never be
read into a prompt, printed, logged, committed, or copied into the checkout.
The maintainer uploads its existing contents as **`SPARKLE_ED_PRIVATE_KEY`** using
stdin or the GitHub secrets UI. Sparkle 2.10.1's new format is already base64 of a
32-byte seed; do not encode it again. Maintain an encrypted offline backup under
maintainer control. Only the public key belongs in Git. Never regenerate the
production key as part of setup or CI.

Both release tasks remove signing credentials from child environments.
Sparkle receives its key only through stdin (`--ed-key-file -`); its children do
not inherit it. Both Sparkle tools' stdout/stderr are captured and suppressed,
since malformed-key diagnostics can reveal input. No key or raw diagnostic file
is created by the feed task. Cleanup guards remove its temporary archives on
exit, including interruption by SIGINT or SIGTERM.
Apple keys are decoded into private temporary files and removed after
use; the Apple CLI still receives certificate/keychain passwords and public API
identifiers as arguments, so the dedicated runner must be trusted.

For rotation, retain the old key and follow [Sparkle's key rotation guidance](https://sparkle-project.org/documentation/#rotating-signing-keys).
Do not simply replace the committed key and Actions secret: existing clients
trust the old key, and this feed is signed too. Plan and test a bridge release
with the same Developer ID and a separately hosted old-key-signed feed leading
to an app configured for the new key/feed. Keep that bridge and old feed available
for older clients. Update the committed public key and any override together,
and then switch the secret only for releases using the new key. This requires a
reviewed migration beyond the normal single-key workflow; losing the old key is
not grounds to publish an unsigned item. Sparkle's documented Developer ID DMG
fallback and signed-feed failure expiration also need testing before use.

### Production and hosting flow

1. `release-macos.yml` checks out the exact stable tag, verifies its Cargo version,
   builds without signing secrets, signs inside-out, notarizes/staples the app,
   creates the DMG, and notarizes/staples that DMG. Only the final stapled bytes
   are hashed and signed for updates. The intermediate ZIP exists solely for app
   notarization; it is not a release asset or appcast enclosure. No deltas ship.
2. `cargo xtask macos release-notes` writes `dist/RELEASE_NOTES.md` from non-merge
   commit subjects since the previous reachable stable tag, omitting authors and
   commit bodies. Run it after packaging: `dist/.notarized` selects
   `packaging/macos/RELEASE_NOTES.md`; without that marker it uses
   `packaging/macos/RELEASE_NOTES.unnotarized.md` with first-launch workarounds.
   `cargo xtask macos fetch-appcast dist/previous-appcast.xml` then retrieves
   the highest numeric stable release with an appcast, across all API pages.
   Drafts/prereleases and older releases without feeds are excluded. It checks
   every enclosure and release-notes URL/length against published asset metadata.
   Only a confirmed absence of any release feed permits the empty initial feed;
   network, authentication, download, and malformed-feed errors fail the job.
3. `cargo xtask macos appcast` requires the private key, framework, history file,
   notarization marker, matching tag, checksum, and stapled ticket. It seeds the
   output with the previous feed and invokes pinned `generate_appcast` with
   `--maximum-versions 0 --maximum-deltas 0`, preserving all historical items.
   New versions must increase strictly. Sparkle derives `sparkle:version`,
   `sparkle:shortVersionString`, and `sparkle:minimumSystemVersion` from the bundle
   (currently macOS 13.0). It signs the full DMG and escaped HTML release notes,
   and signs the resulting XML. Links use immutable version-specific GitHub
   release assets, e.g. `.../releases/download/v0.3.0/Voxelite.dmg` and
   `.../releases/download/v0.3.0/Voxelite.html`.
4. `sign_update --verify` checks the generated XML signature. The offline checker
   checks canonical 64-byte signatures, exact GitHub URLs, local DMG/notes byte
   lengths, bundle metadata, newest-first ordering, and unchanged prior items.
   It checks structure/lengths, not Ed25519 cryptography; real signature checks
   belong to the pinned Sparkle tools and the installed client. The generated
   feed is copied to `site/appcast.xml` without reserialization.
5. The workflow creates a draft, uploads `Voxelite.dmg`, its checksum,
   `Voxelite.html`, and `appcast.xml`, then publishes. Existing releases/drafts
   make creation fail; no asset is overwritten. A successful **Release macOS**
   workflow triggers **Deploy site** through `workflow_run`, which works even
   when publication uses `GITHUB_TOKEN`. The deploy builds trusted `main`, only
   accepts successful owner-triggered release runs from this repository, and
   shares the existing production concurrency group with main/manual builds.
6. The site fetches the highest stable appcast using the same helper, then
   `crates/voxelite-site` preserves those bytes both in place and for another
   output directory. The build stages the feed at the root of the `site-dist`
   artifact/branch. The Vercel project has no Git integration, so the workflow's
   last step deploys that directory to production with the Vercel CLI (needs the
   `VERCEL_TOKEN` repo secret). Vercel then serves it at `/appcast.xml`, with RSS
   content type and revalidation cache headers.
   Do not minify or rewrite signed XML or HTML notes.

Release assets are the single source of truth: no bot commits to `main`, new
credentials, or mutable server-side feed state. Keeping all prior items allows
Sparkle to select a compatible older update when a later release raises its OS
requirement. Numeric version selection avoids a GitHub “latest” toggle or a new
release without an appcast rolling the feed back. Site builds fail closed on
fetch/validation errors, leaving the existing deployment intact. A site failure
after publication is retried by manually running **Deploy site** on `main`, not
by republishing the release. The trigger must already be merged to `main` before
releasing. See [GitHub workflow_run semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).

Offline checks, without network access or credentials:

```sh
cargo xtask macos check-appcast site/appcast.xml --allow-empty
# After generating a real release locally or in CI:
cargo xtask macos check-appcast site/appcast.xml \
  --release-dir dist --previous dist/previous-appcast.xml
cargo test -p xtask --locked
```

### Release plans without Apple tools

`cargo xtask macos package --dry-run` works on Linux and macOS. It prints the
complete redacted command plan, including cleanup, without executing tools,
downloading Sparkle, building the app or changing `dist/`. `--skip-build` omits
the two app/server builds from that plan. Signing follows `MACOS_SIGNING_MODE`:
`adhoc` ignores credentials; `auto` selects Developer ID only with both certificate
variables, and notarizes only when all three Apple API variables are also set.

Use fake values to inspect the signed plan without exposing real keys to Cargo:

```sh
cargo xtask macos package --dry-run
MACOS_SIGNING_MODE=adhoc cargo xtask macos package --dry-run
MACOS_SIGNING_MODE=auto \
MACOS_CERTIFICATE_P12_BASE64=Zml4dHVyZQ== MACOS_CERTIFICATE_PASSWORD=fixture \
APPLE_API_KEY_P8_BASE64=Zml4dHVyZQ== APPLE_API_KEY_ID=fixture APPLE_API_ISSUER_ID=fixture \
cargo xtask macos package --dry-run
TAG=v0.3.1 SPARKLE_ED_PRIVATE_KEY=fixture cargo xtask macos appcast --dry-run
```

The appcast dry run describes its artifact/history checks and prints both Sparkle
commands, with private-key stdin redacted. It does not require a built release,
write GitHub outputs or generate a feed. The
[xtask command ownership table](../xtask/README.md#release-command-ownership)
maps each external operation to its Rust implementation.

For real credentials, first build with `cargo build --release --locked -p xtask`
in an environment without signing secrets. Then invoke the prebuilt binary:
`target/release/xtask macos package --skip-build` and
`target/release/xtask macos appcast`. Release CI follows this ordering; it also
uses `target/release/xtask version --check-tag "$TAG"` before building the app.
xtask removes all seven signing variables from every child environment and sends
the Sparkle key only on stdin. Temporary secrets use 0600 files in a 0700
directory. Keychain deletion and search-list restoration run after failures,
panics, SIGINT (130) and SIGTERM (143). On Unix, interruption stops the active
tool and its descendants before cleanup; failed cleanup returns 1 and invalidates
`dist/.notarized`. Abrupt machine loss or SIGKILL cannot run process cleanup.

### Local end-to-end test with a throwaway key

Use a disposable checkout and a separate macOS user account. Never use the
production key or overwrite the production public key in your normal checkout.
Download Sparkle **2.10.1** to an external temporary directory and verify the
SHA-256 from `xtask/src/macos/package.rs` before extracting or executing it:

```sh
set +x
sparkle_test=$(mktemp -d)
curl --fail --location --proto '=https' --tlsv1.2 \
  https://github.com/sparkle-project/Sparkle/releases/download/2.10.1/Sparkle-2.10.1.tar.xz \
  --output "$sparkle_test/Sparkle.tar.xz"
printf '%s  %s\n' \
  1a856d2a9edb8e628de88121d7be04cf0e2167f8641650b78fca00b14244cf27 \
  "$sparkle_test/Sparkle.tar.xz" | shasum -a 256 --check
# Continue only if the digest matches.
tar -xf "$sparkle_test/Sparkle.tar.xz" -C "$sparkle_test"
"$sparkle_test/bin/generate_keys" --account voxelite-local-update-test
"$sparkle_test/bin/generate_keys" --account voxelite-local-update-test -p \
  > packaging/macos/sparkle_public_ed_key.txt
(umask 077; "$sparkle_test/bin/generate_keys" --account voxelite-local-update-test \
  -x "$sparkle_test/test-private-key.txt")
```

In that disposable checkout, change the packager's `SUFeedURL` to
`http://127.0.0.1:8091/appcast.xml` **before signing**, and use a test bundle
identifier (e.g. `co.worldwidewebb.voxelite.update-test`) to isolate preferences.
If macOS transport security blocks HTTP, add a loopback-only test ATS exception
in that disposable plist; production must keep HTTPS. Unset the public-key
override or set it to the throwaway public key.

Build two packages using `VERSION=0.0.1 MACOS_SIGNING_MODE=adhoc
cargo xtask macos package`, then `VERSION=0.0.2 MACOS_SIGNING_MODE=adhoc
cargo xtask macos package`. Preserve each app outside `dist` before rebuilding
(the packager clears `dist`). Copy the older app into a writable Applications
folder. ZIP only the newer app into a separate HTTP directory; do not put the
private key under the served directory:

```sh
mkdir "$sparkle_test/http"
ditto -c -k --keepParent /path/to/newer/Voxelite.app "$sparkle_test/http/Voxelite.zip"
"$sparkle_test/bin/generate_appcast" --ed-key-file - --maximum-deltas 0 \
  --download-url-prefix http://127.0.0.1:8091/ "$sparkle_test/http" \
  < "$sparkle_test/test-private-key.txt" > /dev/null 2>&1
"$sparkle_test/bin/sign_update" --ed-key-file - --verify "$sparkle_test/http/appcast.xml" \
  < "$sparkle_test/test-private-key.txt" > /dev/null 2>&1
python3 -m http.server 8091 --bind 127.0.0.1 --directory "$sparkle_test/http"
```

Start the older installed app and invoke both the app menu and Settings button.
Verify Sparkle shows 0.0.2, disables duplicate checks, asks before downloading,
installs, relaunches, and reports no update on a second check. Delete only the
test identifier's `SULastCheckTime` preference to test automatic launch checks.
Alter one archive byte and confirm signature rejection; stop the server and
confirm a recoverable failure. Do not use the production checker for this local
ZIP/HTTP feed: it intentionally only accepts production GitHub DMG URLs.

Ad-hoc ZIP testing exercises updater plumbing, not Gatekeeper or Developer ID
identity continuity. Repeat the flow with Developer ID signed/notarized DMGs and
the throwaway Sparkle key before release, including a quarantined download,
installation into `/Applications`, relaunch, and an offline launch. Clean up the
test user's preferences, throwaway Keychain account, checkout, and temporary
files. Do not upload throwaway assets or keys to GitHub.

### Signed-release checklist

- Merge packaging and site workflows to `main`; set the `VERCEL_TOKEN`
