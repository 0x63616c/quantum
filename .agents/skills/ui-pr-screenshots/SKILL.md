# UI PR screenshots

Every PR that changes the UI shows **Before | After** screenshots of the key screens,
generated by a tool rather than pasted by hand, inside a PR description that follows
[the PR template](../../../.github/pull_request_template.md). Reviewers should be able
to judge the change from the PR page alone.

## 1. Write the PR body from the template

Keep the template's sections and order: `Closes #N`, **Summary** (plain English, 1–3
sentences), **Changes** (bullets), **Testing**, **Checklist**. Do not add a Screenshots
section by hand. The tool inserts it, so non-UI PRs never have an empty one.

## 2. Generate the screenshots

```sh
# Local preview: base = merge-base with origin/main, head = your working tree
cargo xtask screenshots
open target/pr-screenshots/screenshots.md   # images under before/ and after/

# Explicit refs, a subset of screens
cargo xtask screenshots --base origin/main --head my-branch --screen welcome
cargo xtask screenshots --screen 'settings-*'
cargo xtask screenshots --screen 'panels-*' --screen 'dialogs-about-*'

# Publish key screens plus the PR's Screens: line (only changed PNGs enter Git)
cargo xtask screenshots --publish 123
```

- No `--screen` means just `welcome`, `editor-dark` and `editor-light`. All other
  surfaces are opt-in. Repeated `--screen` options select exactly their combined
  matches, deduplicated in registry order. Exact names and a single trailing `*`
  are supported; quote patterns in the shell. Unknown names and patterns matching
  nothing fail before capture. `--screen '*'` explicitly selects all surfaces.
- Migration PRs must select every surface they change, in both themes. Add one
  plain line starting at column zero in the PR body, outside the generated
  Screenshots section, for example `Screens: panels-* settings-general-*`.
  These selectors add to the three key screens. A missing or empty line keeps
  just the key set; duplicate lines fail. This is a whitespace-separated list,
  not shell syntax: no quotes, commas, commands or other glob operators.
- `--publish` reads this line automatically unless explicit `--screen` options
  override the selection. For a local preview of the same selection, use
  `gh pr view 123 --json body -q .body > target/screenshot-pr-body.md` then
  `cargo xtask screenshots --pr-body target/screenshot-pr-body.md`.
  `--pr-body` cannot be combined with `--screen`.
- Runs on Linux only (Xvfb + Mesa lavapipe) so pixels are reproducible: fixed window
  sizes, dark/light themes, the bundled Autumn Workshop example, a fresh data dir (no
  recents), the pointer parked off-window. Needs `xvfb xdotool imagemagick dbus
  mesa-vulkan-drivers`, plus `gh` for `--publish`. Use the agent box or CI, not the
  Mac: `screencapture` over SSH lacks Screen Recording permission and would show the
  wallpaper.
- The **PR screenshots** workflow runs the publish step automatically for PRs that
  touch UI paths. It reads the current PR body as data and validates selectors in
  xtask, without evaluating shell code. Body edits alone do not trigger capture;
  after editing the line, push or re-run from the Actions tab (`workflow_dispatch`,
  PR number). The optional `screens` dispatch field replaces the body's extra
  selectors for that run, using the same space-separated syntax; blank uses the
  body. Key screens are always included in CI. Local `--publish` also works.
- Only changed, added or removed screens and their useful zoom crops are committed
  to the orphan-style `pr-assets` branch at
  `pr-<N>/<head-sha>/{before,after}/<screen>.png` and linked through
  `raw.githubusercontent.com/<repo>/<assets-commit>/…`, so links never move. Never
  force-push `pr-assets`; the tool appends commits and retries on races.
- Unchanged screens are listed as text under **Unchanged screens**, without image
  links. Their PNGs stay in local output and CI artifacts. An entirely unchanged
  run updates the PR summary without pushing an assets commit. Existing published
  history is preserved.

## 3. Add or change a capture surface

Screens live in `SCREENS` in `xtask/src/screenshots.rs` (key flag, name, caption,
window-title regex, fixed size, app args). New launch states are opt-in (`key: false`)
so adding coverage does not increase every UI PR's capture cost. Add one when a PR
introduces a new window or panel that the existing screens do not show. If the state
needs input (a dialog, a hover), add a CLI flag or fixture to the app rather than
scripting clicks, so it stays deterministic.

The app's development-only `--show <state>` opens the bundled example directly in
an editor surface or a Settings page. The complete state list and manual/platform
exclusions are in [the app README](../../../crates/quantum-app/README.md#ui-capture-states).
Use `chrome-menu-*`, `panels-*`, `dialogs-*`, `popovers-*`, `overlays-debug` and
`settings-*` states. Each entry in the `screens!` registry expands into both
`<state>-dark` and `<state>-light`; select both with `--screen 'dialogs-about-*'`,
or use exact names such as `--screen dialogs-about-dark --screen dialogs-about-light`.
Editor states use 1440×900. Settings targets `^Quantum Settings$` at 880×640;
About stays in the editor. Keep the established Welcome/editor captures unchanged.
The capture script runs in a private data directory with a stable relative socket
name; any file fixture args must therefore use absolute paths. Check every new
PNG for the intended surface. A base binary without `--show` will correctly show
“not on this side” for these new states.

## 4. Check the result on GitHub before asking for review

1. Open the PR page (`gh pr view <N> --web`, or fetch it) and confirm every image
   loads, Before and After are the same size side by side, captions read clearly, and
   unchanged screens sit collapsed under **Unchanged screens**.
2. Look at the images, not just the table. Small changes get an extra row cropped
   to the changed area and enlarged, so check that row too. A screen marked *changed* that you did
   not mean to change is a regression; fix it or explain it in **Changes**.
3. Tick the UI checklist items only after doing the above.

## Headless regression gate

Before/after PR screenshots remain the design review evidence. The independent
`cargo xtask ui-snapshots` gate renders production GPUI views on Linux through
`HeadlessAppContext` and lavapipe without DISPLAY, WAYLAND_DISPLAY, or Xvfb.
It checks committed references in `crates/quantum-app/tests/ui-goldens/`.

Run `cargo xtask ui-snapshots` after UI changes. For an intentional appearance
change, run `cargo xtask ui-snapshots --rebaseline --screen 'settings-*'` (or omit
the filter for every key screen), inspect every changed PNG in both themes, and
commit the references with the change. Only `--rebaseline` writes goldens; CI
never accepts them automatically. Failures leave actual/expected/diff images in
`target/ui-snapshots/` and upload them as CI artifacts. Review focus/hover/pressed,
empty/loading states and long-label truncation as well as the default snapshots.
See [UI snapshots](../../../docs/ui-snapshots.md) for coverage and tolerance.

Native macOS goldens from the closed draft #194 are parked as an optional later
addition. This gate does not need a macOS GUI session and does not verify AppKit
chrome, Core Text rasterization, or the Metal viewport/surface handoff.

## Troubleshooting

- `no window titled /…/ appeared`: the app crashed or the window title changed. The
  script prints the app log; update the title regex in `SCREENS` if it was renamed.
- Every screen differs slightly: something animates. Raise `PR_SHOTS_SETTLE` (seconds,
  default 6) or make the animation settle under capture.
- A screen is new or was removed: its row shows "not on this side". That is expected
  for new windows.
